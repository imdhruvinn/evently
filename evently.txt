================================================================================
EVENTLY - THE DEFINITIVE ARCHITECTURE & ENGINEERING GUIDE
================================================================================

This document is the absolute "source of truth" for the Evently project. It explains not just WHAT the system does, but exactly WHY specific technologies were chosen over others, HOW they work under the hood, and WHERE the code is located in the repository.

--------------------------------------------------------------------------------
1. THE CORE STACK: CHOICES & ALTERNATIVES
--------------------------------------------------------------------------------

FRONTEND: Next.js 15 (App Router) + TypeScript + Vanilla CSS
- WHY THIS: Next.js provides Server-Side Rendering (SSR) which is crucial for SEO (so events show up on Google) and fast initial page loads. The App Router (`frontend/src/app`) allows for streaming components and better layouts compared to raw React. Vanilla CSS was chosen with CSS variables for the "Glassmorphism" look to have total control over the design without the overhead of heavy UI libraries.
- WHERE: `frontend/src/app/*` (Pages), `frontend/src/components/*` (Reusable UI).
- ALTERNATIVES: We could have used Vite + React (but would lose SEO/SSR out of the box), or Vue/Nuxt.

BACKEND: Node.js + Express.js + TypeScript
- WHY THIS: Node.js is non-blocking and event-driven, making it perfect for high I/O operations (like handling thousands of concurrent booking requests). Express is the standard, stable routing framework.
- WHERE: `backend/src/index.ts` (Entry point), `backend/src/controllers/*` (Logic).
- ALTERNATIVES: Go/Rust (faster but harder to share types with frontend), Python/Django (slower for high concurrency WebSockets/async tasks).

DATABASE ORM: Prisma
- WHY THIS: Prisma provides complete type safety. When we query the database, TypeScript knows exactly what fields exist. This prevents runtime crashes. It also handles migrations easily.
- WHERE: `backend/prisma/schema.prisma` (The entire database blueprint).
- ALTERNATIVES: TypeORM or Sequelize (older, less type-safe), or Raw SQL (prone to injection attacks and typos).

DATABASE: PostgreSQL
- WHY THIS: Ticketing systems require STRICT ACID compliance (Atomicity, Consistency, Isolation, Durability). We cannot afford data corruption where two people buy the same seat. Postgres handles complex transactions and locks perfectly.
- ALTERNATIVES: MongoDB (NoSQL is bad for relational data like Users -> Bookings -> Seats -> Events).

CACHE & QUEUE: Redis + BullMQ
- WHY THIS: When 10,000 people try to book at once, the database would crash. Redis is an in-memory datastore (microsecond reads). We use it for rate limiting and distributed locks. BullMQ uses Redis to queue background jobs (like sending emails) so the user doesn't wait.
- WHERE: `backend/src/lib/redis.ts`, `backend/src/services/jobQueue.ts`.
- ALTERNATIVES: RabbitMQ or Kafka (too complex to set up for this scale), AWS SQS (adds cloud lock-in).

--------------------------------------------------------------------------------
2. SECURITY & AUTHENTICATION (HOW IT WORKS)
--------------------------------------------------------------------------------

A. JSON Web Tokens (JWT) & bcrypt
- HOW IT WORKS: When a user registers, `bcrypt` hashes their password with a "salt" (so even if the DB is stolen, passwords can't be read). On login, the server generates a JWT (a cryptographically signed string). The frontend stores this token and sends it in the `Authorization: Bearer <token>` header for every request.
- WHERE: `backend/src/utils/jwt.ts` and `backend/src/middleware/auth.ts`.
- ALTERNATIVES: Session Cookies (harder to scale across multiple mobile apps/servers).

B. Multi-Factor Authentication (MFA / 2FA)
- HOW IT WORKS: We use the `otplib` package. The server generates a random base32 secret. We convert this to a QR code. Google Authenticator scans it. The app and the server use the current exact Time + Secret to generate the same 6-digit code.
- WHERE: `backend/src/controllers/authController.ts` (toggleMfa function).

C. Rate Limiting (DDoS Protection)
- HOW IT WORKS: Using `express-rate-limit` with a Redis store. If an IP address hits the login route more than 5 times in 15 minutes, Redis blocks them. This stops hackers from brute-forcing passwords.
- WHERE: `backend/src/middleware/rateLimiter.ts`.

--------------------------------------------------------------------------------
3. HIGH CONCURRENCY: PREVENTING DOUBLE BOOKINGS
--------------------------------------------------------------------------------

This is the hardest part of ticketing. How do we stop two people from buying the last ticket at the exact same millisecond? We use TWO methods depending on the event type:

METHOD 1: Optimistic Concurrency Control (OCC) - For General Admission
- HOW IT WORKS: The `Event` table has a `version` integer. When booking, we do:
  `UPDATE event SET capacity = capacity - 1, version = version + 1 WHERE id = 1 AND version = 5`.
  If User A and User B both see version 5, User A's update succeeds (version becomes 6). User B's update fails because version 5 no longer exists. User B gets an error and the system safely retries.
- WHERE: `backend/src/utils/retry.ts` (`withOptimisticLocking`).
- ALTERNATIVES: Pessimistic Locking (locks the whole row, making the database incredibly slow for everyone else).

METHOD 2: Distributed Redis Locks - For Assigned Seating (Row A, Seat 1)
- HOW IT WORKS: If two people click "Seat A1", the server tries to create a key in Redis: `SET seat-lock:A1 userId EX 30 NX`. `NX` means "Only set if it does NOT exist". Redis is single-threaded, so it perfectly guarantees only one person gets the lock. The loser gets a "Seat already being booked" error immediately.
- WHERE: `backend/src/services/seatBookingQueue.ts`.

--------------------------------------------------------------------------------
4. THE TICKET SYSTEM (PDF & QR CODES)
--------------------------------------------------------------------------------

- HOW THE QR WORKS: We don't just put a URL in the QR code (anyone could fake that). We use `jsonwebtoken` to sign a special payload containing the `bookingId`. We sign it using our `JWT_SECRET`.
- HOW THE PDF WORKS: We use `jsPDF` on the backend to programmatically draw a ticket. We place the user's name, event details, and embed the generated QR code image as a PNG into the PDF. It's sent to the frontend as a binary Blob.
- HOW SCANNING WORKS: The frontend `/verify-ticket` page asks for camera access. It scans the QR. It sends the scanned token to the backend. The backend verifies the cryptographic signature. If someone photoshopped a fake ticket, the signature won't match, and it fails.
- WHERE: `backend/src/services/ticketService.ts`.

--------------------------------------------------------------------------------
5. BACKGROUND JOBS & ASYNC PROCESSING
--------------------------------------------------------------------------------

- THE PROBLEM: Sending an email via Gmail SMTP takes 2-3 seconds. Generating a PDF takes 1 second. If we do this while the user clicks "Book", the website will freeze.
- THE SOLUTION: Fire-and-forget background processing.
- HOW IT WORKS: In the booking controller, once the database transaction is saved, we return a `200 OK` to the frontend instantly. Then, we use `setImmediate()` or `setTimeout()` in Node.js to trigger the email sending and PDF generation in the background.
- EMAILS: We use `nodemailer` to connect to Gmail via an App Password. We use custom HTML templates for a premium look (Green for Confirmed, Red for Cancelled).
- WHERE: `backend/src/controllers/bookingController.ts` (The timeouts at the end) and `backend/src/services/emailService.ts`.

--------------------------------------------------------------------------------
6. FRAUD DETECTION SYSTEM
--------------------------------------------------------------------------------

- HOW IT WORKS: We have a heuristic rules engine that intercepts bookings.
  1. Velocity Check: Did this user make > 3 bookings in the last 5 minutes?
  2. Volume Check: Are they trying to buy > 15% of the total event capacity?
- If true, it flags the transaction in the Audit Logs for admin review.
- WHERE: `backend/src/services/fraudService.ts`.

--------------------------------------------------------------------------------
7. ARCHITECTURE & FOLDER STRUCTURE EXPLAINED
--------------------------------------------------------------------------------

BACKEND STRUCTURE (Model-Route-Controller-Service):
- `prisma/schema.prisma` -> The database models.
- `src/routes/*` -> Defines the URL endpoints (e.g., POST /api/bookings).
- `src/controllers/*` -> Handles the HTTP request/response. Validates input.
- `src/services/*` -> The heavy lifting. Reusable business logic (e.g., FraudService, EmailService).
- `src/middleware/*` -> Intercepts requests (Auth checks, Error handlers, Rate limiters).
- `src/utils/*` -> Helper functions (JWT tools, OCC retry logic).

FRONTEND STRUCTURE:
- `src/app/page.tsx` -> The Landing Page.
- `src/app/events/[id]/page.tsx` -> Dynamic route for a specific event.
- `src/components/*` -> Reusable pieces (Navbar, Modals, Buttons).
- `src/lib/api.ts` -> The central file that makes `fetch` requests to the backend. It automatically attaches the JWT token from localStorage to every request.

--------------------------------------------------------------------------------
SUMMARY
--------------------------------------------------------------------------------
Every piece of this architecture exists to solve a specific enterprise problem. Redis prevents bot attacks and double-booking. Prisma prevents SQL injection. Next.js provides SEO. BullMQ/setImmediate prevents UI freezing. Cryptographic QR codes prevent forgery. OCC guarantees capacity limits. This is a complete, production-ready system.
